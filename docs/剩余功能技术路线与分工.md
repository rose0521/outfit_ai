# 剩余功能技术路线与分工（两周版）

> 目标：两周内交一个能演示的课程 demo。范围 = 商品检索 + 质量评估 + 穿搭推荐，串成一个最小闭环；自然语言交互作为加分项；**虚拟试穿砍掉**（最后 PPT 放一页"后续计划"即可）。

## 0. 交付标准（验收脚本）

演示时走这么一条路，走通就算完成：

1. 输入一句话（"白色通勤衬衫"）或一张图 → 检索出相关商品（带图、价格、质量分）
2. 点开某件商品 → 看质量评估（好评率 + 优缺点摘要）
3. 把 2~5 件加进"搭配区" → 给出搭配打分 / 补全推荐
4. （加分）全程用自然语言对话完成

## 2. 各模块技术路线

### M0 数据接入与特征提取（地基，约 2 天，关键路径）

**要确认的字段（拿到数据第一件事，逐项核对）：**

| 字段 | 用途 | 缺失怎么办 |
| --- | --- | --- |
| `item_id` | 商品唯一标识 | 没有就用图片名/行号自造，但必须唯一稳定 |
| `image`（文件或 URL） | 提特征、展示 | 没有图片则整个项目无法做，需换数据集 |
| `rating`（评分） | 质量评估 L1 | 没有就用评论文本情感推断 |
| `review_text`（评价文本） | 质量评估 L2 | 没有则质量评估只做 rating 统计 |
| `category`（类目） | 检索过滤、穿搭约束 | 没有则检索不做类目过滤，影响不大 |

**做法：**

现在的 `scripts/extract_features.py` 是读 Polyvore parquet 内嵌图片字节的，**不能直接用**，要写一个适配脚本（命名建议 `scripts/extract_catalog_features.py`）：

1. 读入清单（csv / json：`item_id, image_path/url, ...`）
2. 逐条读图（文件或下载 URL）→ `PIL.Image.open(...).convert("RGB")`
3. 走和现有脚本**完全相同的推理路径**（保证特征空间一致）：

```python
# 视觉侧（与 extract_features.py 保持一致，跨版本稳定）
from transformers import CLIPModel
model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
# 用 CLIPProcessor 预处理成 pixel_values
vision_out = model.vision_model(pixel_values=pixel_values, return_dict=True)
feats = model.visual_projection(vision_out.pooler_output)   # (N, 512)
feats = feats / feats.norm(dim=1, keepdim=True)             # L2 归一化
```

4. 输出与现有格式**完全一致**，这样下游（serve_demo、检索、穿搭）零改动复用：

```
data/catalog/
├── item_ids.json      # ["1000001", ...]，与特征行一一对应
├── features.npy       # (N, 512) float32，已 L2 归一化
├── items.json         # 元数据：{item_id: {title, price, image_url, category, rating, reviews:[...]}}
└── failed.json        # 读图失败的记录
```

**注意：**
- 特征必须 L2 归一化，否则后面余弦相似度＝点积 的前提不成立。
- 图片规模大时用 `--num-workers` 多进程（沿用现有脚本的 spawn 模式，Windows 下安全）。
- 这是**风险最高、最耗时**的一步，第 1 天就把脚本写出来先对 100 张图跑 smoke，再全量。

### M1 商品检索（CLIP 图文检索，约 2 天，依赖 M0）

**原理：** 已有 512 维图片特征且已归一化，查询（文字或图片）也编码到**同一个 512 维空间**，算点积就是余弦相似度，取 top-k。

**文字 → 图：**

```python
# 文本侧：走 text_model → pooler_output → text_projection，与图片侧对称
tok = CLIPTokenizer.from_pretrained("openai/clip-vit-base-patch32")
inputs = tok([query], return_tensors="pt", padding=True, truncation=True)
text_out = model.text_model(**inputs)
q = model.text_projection(text_out.pooler_output)   # (1, 512)
q = q / q.norm(dim=1, keepdim=True)
scores = features @ q[0]                            # (N,)
topk = scores.argsort()[::-1][:top_k]
```

**图 → 图：** 用户上传图 → 走 M0 同一段视觉推理 → 得到 512 维 → 同样算 `features @ q`。

**索引：**
- demo 规模（几万件）用 numpy 矩阵全量点积就够，`70000×512 @ 512` 是毫秒级，**不要一开始就上 faiss**。
- 若后面规模到几十万再换 `faiss-cpu` 的 `IndexFlatIP`（归一化向量用内积），作为可选优化。

**新增接口（加进 `serve_demo.py`）：**

```
POST /api/search
请求：{"query": "白色通勤衬衫", "top_k": 20}        # 文字检索
     {"image_url": "...", "top_k": 20}              # 图搜图（或 base64）
可选：{"category": "tops"}                           # 类目过滤
响应：{"results": [{"item_id","score","title","image_url","price","avg_rating","positive_rate"}, ...]}
```

**交付物：** `scripts/search_index.py`（启动时加载特征+元数据，构建矩阵）＋ serve 里的 `/api/search` 端点。

### M2 质量评估（评价 → 质量分 + 摘要，约 3 天，依赖 M0 元数据）

分两层，L1 保底，L2 出彩。

**L1 基础（必做，半天）：rating 统计**

```python
avg_rating   = mean(ratings)                        # 平均分
positive_rate = sum(r >= 4 for r in ratings) / n    # 好评率（阈值按评分制调）
review_count = n
```
纯 pandas 搞定，输出写进 `items.json` 每件商品的 `quality` 字段。

**L2 文本分析（加分，约 2 天，用 LLM API）：**

对每件商品抽样 **top 20 条**评论（不用全量，控成本），批量丢给 LLM 做方面级情感。用现成 API（DeepSeek / 通义千问 / OpenAI 任选一个有 key 的，建议 DeepSeek，便宜且中文好）。

Prompt 骨架：

```
你是电商质检助手。下面是一件女装商品的若干条用户评价，请从这几个方面判断：
面料、尺码、色差、做工，以及整体评价。
对每个方面输出：sentiment（positive/neutral/negative）+ 依据；最后给一句话优缺点总结。
输出严格 JSON：
{"aspects":{"面料":{...},"尺码":{...},"色差":{...},"做工":{...}},
 "summary":"一句话总结"}
评价列表：
1. ...
```

输出结构化结果缓存到 `items.json`（或独立 `quality.json`），避免重复调 API。

**新增接口：**

```
GET /api/item/{id}/quality
响应：{"item_id","avg_rating","positive_rate","review_count",
       "aspects":{"面料":{"sentiment":"positive"}},"summary":"..."}
```

**交付物：** `scripts/quality_assess.py`（L1 统计 + L2 批量调 LLM + 结果落盘）。

### M3 穿搭推荐接入（约 1 天，基本是"接"）

现有 `serve_demo.py` 已经有 `/api/outfit/score` 和 `/api/outfit/fill`，模型是 Polyvore 训练的 MeanPoolMLP。**不重新训练**，直接用零样本迁移：

- 现有 `load_features()` 会把多个目录合并成 `item_id → 512 维` 的查找表，只要把 M0 的 `data/catalog/` 目录**加进 `--feature-dirs`**，新商品就能直接参与打分/补全。
- 效果会打点折扣（新数据没训过），但 demo 够用。**demo 前手动验 3~5 组搭配，别翻车。**

```powershell
python -X utf8 scripts/serve_demo.py --port 8000 \
  --feature-dirs data/processed/clip_features data/processed/clip_features_valid data/processed/clip_features_test data/catalog
```

**交付物：** 无新模型，改启动命令 + 前端调两个接口。

### M4 自然语言交互（加分项，约 2~3 天，依赖前三者有 API）

**推荐方案：LLM function calling**。定义 3 个工具描述（search / get_quality / outfit_score / outfit_fill），LLM 根据用户自然语言决定调哪个、参数是什么，后端执行后把结果回喂 LLM 生成自然语言回复。

```
POST /api/chat
请求：{"message": "帮我找几件通勤的白衬衫，质量好的"}
响应：{"reply": "为你找到 3 件好评率高的白衬衫：...", "results":[...]}
```

**降级方案（更稳，时间紧用这个）：** 不做 function calling，直接让 LLM 输出一个 JSON（`{"intent":"search","query":"白衬衫 通勤","filters":{"min_rating":4}}`），后端按 JSON 路由到已有接口。这样 LLM 只做"意图 + 参数抽取"，出错的概率小很多。

**注意：** 这块是纯增量，不做也不影响主线。两周若紧张，直接砍掉或做个"关键词规则"的假版本。

## 3. 分工建议

按依赖拆，最顺的切法是：

**人 A（数据 + 检索）**：M0 全包 + M1。拿数据集、写适配提取脚本、建索引、加 `/api/search`。这是关键路径，其他人等他的产出。

**人 B（质量评估）**：M2。只依赖人 A 的元数据，可几乎并行。负责 rating 统计 + LLM 文本分析 + `/quality` 接口。

**人 C（前端 + 整合）**：M3 接入 + 前端页面 + （时间够再做）M4。前期人 C 可以先把前端骨架和 Mock 数据搭好，不等人 A。

**若只有 2 人**：A = M0 + M1 + M2；B = M3 + 前端 + M4。M4 直接砍。

**分工铁律：** M0 是唯一堵点，第 1~2 天要么全队一起把它攻下来（分字段确认 / 脚本 / 抽检三件事），要么人 A 做、其余人用 Mock 数据先干别的。

## 5. 风险与应对

1. **数据集字段未知（最大风险）**：拿到数据第一件事就是核对第 M0 节的字段表。若没有图片 → 必须换数据；没有 rating/review → 质量评估降级。**不要假设，先看数据。**
2. **提特征耗时**：几万张图 CPU 可能几小时到一天，GPU 快得多。第 1 天就要把脚本跑起来，别拖到后面。
3. **LLM API 成本/额度**：M2 和 M4 都调 API，注意 key 额度和费用；M2 每件只抽 top 20 条评论控成本。
4. **穿搭零样本迁移效果**：新数据打分可能不稳，演示前手动验几组，必要时挑"好搭"的商品进演示池。
5. **demo 翻车点在演示数据**：宁可提前人工筛一批"检索能中、质量好看、搭配分高"的商品作为演示商品，别现场随机搜。
