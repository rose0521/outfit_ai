## 3. 各模块技术路线

### 3.1 数据落地与元数据（前置，卡点，最先做）

同学那份学术数据集（图片 + 评价）是后面一切的地基。**第一天必须确认字段**，否则全线卡住。

产出：一份 `data/processed/metadata.csv`，每行一件商品：

```csv
item_id,semantic_category,title,price,image_path
100001,tops,白色通勤衬衫,89.0,images/100001.jpg
```

字段说明：`image_path` 为主图本地路径或可下载 URL；`semantic_category` 必须是 11 类之一（映射规则见 `docs/商品库对接说明.md`）。

评价单独一张表 `data/processed/reviews.csv`：

```csv
item_id,rating,review_text
100001,5,"面料不错，版型正"
100001,3,"有点透，尺码偏小"
```

任务：数据清洗（去重、类目映射、rating 规整到 1~5）、生成上面两张表。

### 3.2 CLIP 特征提取（复用已有脚本，但要适配）

现有 `extract_features.py` 读的是 Polyvore 的 parquet（内嵌 `image.bytes`）。新数据集是图片文件/URL，需写一个适配脚本：

`scripts/extract_features_from_files.py` —— 逻辑照搬 `extract_features.py` 的模型加载与推理（`vision_model → pooler_output → visual_projection → L2 归一化`），只把"读 parquet 字节"换成"读 `metadata.csv` 的 `image_path`"。输出格式不变：`data/processed/clip_features_catalog/` 下的 `features.npy` + `item_ids.json`。

要点：

- 沿用同一 CLIP 模型，**不要换模型**，否则和穿搭模型的特征空间不一致；
- CPU 提取慢，demo 只需提用到的子集（几百~几千件），别全量；
- 失败图片写进 `failed.json`，跳过不阻塞。

### 3.3 商品检索（CLIP 文字搜图 / 以图搜图）

**原理**：CLIP 是图文对齐的多模态模型，文字和图片映射到**同一个 512 维空间**。图片特征已经 L2 归一化，所以「文字向量 ⊙ 图片特征」的内积就是余弦相似度。这是现有资产的自然延伸，几乎零训练成本。

文字编码（与图片路径对称，显式走 projection，规避 transformers 版本差异）：

```python
from transformers import CLIPModel, CLIPProcessor
model = CLIPModel.from_pretrained("openai/clip-vit-base-patch32")
proc  = CLIPProcessor.from_pretrained("openai/clip-vit-base-patch32")

def encode_texts(texts: list[str]):
    inputs = proc(text=texts, return_tensors="pt", padding=True, truncation=True)
    with torch.no_grad():
        out = model.text_model(**inputs, return_dict=True)   # CLIPTextModel
        emb = model.text_projection(out.pooler_output)       # (N,512)
    emb = emb.float().cpu().numpy()
    return emb / np.linalg.norm(emb, axis=1, keepdims=True)  # L2 归一化
```

检索（内存矩阵 + numpy，demo 规模足够快，不需要 FAISS）：

```python
feats = np.load("features.npy")           # (N,512) 已归一化
ids   = json.load(open("item_ids.json"))
q     = encode_texts(["白色通勤衬衫"])[0]  # (512,)
score = feats @ q                          # 内积 = 余弦相似度
topk  = np.argsort(-score)[:20]
```

以图搜图同理：把查询图过一遍图片编码（复用 `extract_features.py` 的 `extract_features_raw`），再 `feats @ q`。

**排序后处理（可选但建议）**：给检索结果加「质量分加权」或「类目过滤」，例如用户说"衬衫"时把非 tops 的降权——简单规则即可，别过度设计。

### 3.4 质量评估（评分统计 + 方面级分析）

分两层，**评分统计必做，方面级是加分**。

**第一层（必做，确定性，零成本）**：对 `reviews.csv` 做 pandas 聚合，产出每件的：

- `rating_mean`：平均分（0~1，除以满分）；
- `rating_count`：评价条数；
- `positive_rate`：好评率（rating ≥ 4 占比）。

示例：

```python
g = reviews.groupby("item_id").agg(
    rating_mean=("rating", "mean"),
    rating_count=("rating", "size"),
    positive_rate=("rating", lambda s: (s >= 4).mean()),
)
```

**第二层（加分，离线预计算）**：用 LLM 对"热门商品"的评价做方面级摘要，产出结构化标签：

```json
{
  "item_id": "100001",
  "aspects": {"面料": 0.8, "尺码": 0.5, "色差": 0.9, "做工": 0.7},
  "pros": ["面料舒服", "版型正"],
  "cons": ["尺码偏小"]
}
```

实现要点（关键，决定成本与稳定性）：

- **离线批量预计算，绝不在查询时调 LLM**：只对 demo 会用到的几十~几百件商品跑，结果缓存成 `data/processed/quality_cache.json`，服务启动时读进内存；
- 用 OpenAI 兼容接口即可，国内可用 DeepSeek / 通义千问 / 文心（一个 `base_url` 参数切换），有 VPN 用 GPT/Claude 也行；
- 给 LLM 的 prompt 固定「输出 JSON」格式，并给几个 few-shot 例子，避免解析失败；
- **保底降级**：没 API key / 网络不通时，退回关键词规则（"掉色/色差"→色差，"偏大/偏小"→尺码），照样能演示。

### 3.5 穿搭推荐整合（已有，只接线）

`/api/outfit/score`、`/api/outfit/fill` 已实现。唯一要做的是：确保检索回来的商品的 `semantic_category` 是 11 类之一、且特征已在 `clip_features_catalog/` 里——两者满足即可直接打分，无需改模型。

### 3.6 自然语言交互（加分，两条路）

**保底（规则匹配，零成本，先做）**：按关键词路由——"搜/找/有没有"→检索；"评价/质量/好不好"→质量评估；"搭不搭/推荐/补"→穿搭。确定性、可演示、不依赖外部 API。

**加分（LLM function calling）**：把「检索、质量、穿搭」三个接口定义成 tools（JSON schema），LLM 决定调哪个。用 OpenAI 兼容 API（同上）。本质是胶水层，前面有 API 了再挂。

## 4. 接口契约（并行开发的依据）

在现有 `serve_demo.py` 上**新增**三个接口，前端与后端按此契约并行开发：

### `POST /api/search` —— 检索

请求（文字 或 图片，二选一）：

```json
{"query": "白色通勤衬衫", "top_k": 20}
// 或 {"image": "<base64>", "top_k": 20}
```

响应：

```json
{"results": [
  {"item_id": "100001", "score": 0.71, "title": "白色通勤衬衫",
   "price": 89.0, "image_url": "images/100001.jpg", "rating_mean": 0.82, "rating_count": 12}
]}
```

### `GET /api/quality/{item_id}` —— 质量评估

```json
{"item_id": "100001", "rating_mean": 0.82, "rating_count": 12, "positive_rate": 0.75,
 "aspects": {"面料": 0.8, "尺码": 0.5}, "pros": ["面料舒服"], "cons": ["尺码偏小"]}
```

`aspects/pros/cons` 无 LLM 时可为空对象/空数组，前端据此决定是否展示。

### `POST /api/chat` —— 自然语言（加分）

```json
{"message": "帮我找一件白衬衫，再帮我看看和这条裤子搭不搭"}
```

响应含 `reply`（自然语言）+ `actions`（实际调用的检索/穿搭结果），前端按 `actions` 渲染卡片。

> 已有接口不变：`/api/outfit/score`、`/api/outfit/fill`、`/api/item/{id}`、`/health`。

## 8. 风险与降级方案

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 数据集缺图片 / 字段不齐 | 全线卡住 | D1 就确认；缺图商品剔除，缺评价字段则只做检索+穿搭 |
| LLM API 网络不通 / 成本 | 方面级做不了 | 保底用关键词规则，质量评估退化为评分统计，demo 仍完整 |
| CPU 提特征太慢 | 拖进度 | 只提 demo 用到的几百件子集 |
| 新数据集类目对不上 11 类 | 检索/推荐乱 | 严格按 `商品库对接说明.md` 映射，对不上的先归 accessories |
| LLM function calling 不稳定 | NL 交互翻车 | 保底规则匹配，LLM 只作增强，坏了不影响主线 |

---

**一句话总结**：两周内只做「检索 + 质量 + 穿搭」三件事的最小闭环，数据表最早交付、特征适配复用现有脚本、质量评估先确定性统计再上 LLM、NL 交互和虚拟试穿是锦上添花。分工上 B 先冲数据，A 并行写脚本，C 全程 Mock 不阻塞。
